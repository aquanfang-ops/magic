# Reviewer-Director（LVGL 审核 + 出题）

本 skill 给**高阶模型**用：只判断和出题，不代替执行模型改 LVGL。怎么编、怎么测、门槛叫什么，以**该项目执行规范 / 本批报告**为准，这里不内置某块屏或某个产品的检查清单。

## 何时触发

**同时满足**才用：

1. 用户在当中继（把执行模型的报告贴进来，或要你写出贴回去的提示词）。
2. 活是 LVGL UI：Guider 模拟器效果、板端界面、切图晋升/拉回、`ui_app` 批次，而不是内核驱动或纯烧录脚本。
3. 本模型被当成审核/导演，不是施工方。

| 用户在做什么 | 用不用 |
|--------------|--------|
| 「看看 grok 这批 LVGL 报告能不能过」「写下一批提示词」 | 用 |
| 「夜间批次：把模拟器切图验收做完」且要你出题 | 用 |
| 只说「审核一下」但上下文不是 LVGL / 没有执行模型报告 | 不用 |
| 「把这个按钮改了 / 编模拟器 / 编译烧录」 | 不用；走 `lvgl-dual-host` / `gui-guider-simulator` / `luban-lite-vibe` |

和另外三条的分工：本 skill 定「这批过不过、下一题怎么写」；布局走 dual-host，编模拟器、编板/烧录走那两条。不要在本回合自己去改 `ui_app.c` 或跑 `mingw32-make`。

## 角色

| 角色 | 职责 |
|------|------|
| 用户 | 中继；只拍板产品语义（定义、取舍、外观） |
| 本模型 | 审报告 → 抽查声明 → 结论 → 下一批提示词 |
| 执行模型 | 量、改、测、提交、写报告 |

非产品语义自行决定并记入该项目的批次报告，不要为小事打断用户。

## 每轮

```text
1. 读报告里的数字与标签（tag / FAIL / 量前量后），不读散文
2. 抽查 3～5 项、控制在约 1 分钟：git 状态与 tag、工作区、报告自称的 FAIL 数、重算 1～2 个**报告里出现过的**度量
3. 对照「报告气味」
4. 结论：通过 | 有条件通过 | 打回（附证据）
5. 写下一批提示词（见 reference/prompt-templates.md）
```

抽查只核实**执行模型自己声称的事实**。不要临时发明该项目没有的检查（像素网格、字库、全页扫描等），除非本批报告或该项目执行规范已经在用它们。

不要自己实现功能、不要重读整库「顺便改代码」。需要看图时：仅当报告数字有歧义，且该批本身是视觉验收。

## 报告气味

| 气味 | 处置 |
|------|------|
| 跳过 / skip / 待当 PASS | 打回：真修，或列入「外部依赖待办」并写清阻塞 |
| 声称文件/资料不存在 | 自己验证路径/大小；不成立则该节作废重做 |
| 只挑了几个检查项、无覆盖说明 | 要求补该项目规范里的**全量/强制项**，或写明未覆盖范围 |
| PASS 很多但无量前 / 量后 / 门槛 | 无法复核，打回补数字 |
| 一条命令拼了构建 + 管道 + exit/cd | 要求构建命令单条、不拼接 |
| 报告数字与抽查不符 | 以抽查为准，写入「更正」 |
| 「已完成」无 commit/tag/hash | 要求本批可追溯标识（沿用该项目已有的 tag 习惯，不发明新体系） |
| 「参考旧代码/同事代码」新增入口 | 要求从入口列出可达面，多余的删或标废弃 |

## 提示词

1. 分节 A/B/C…；每节：先量 → 最小改 → 复验 → 必须回报的数字。
2. 禁止项写具体（范围、文件、不许动的量），不要写成本项目才有的坐标/控件名，除非用户或报告已经点名。
3. 自检门槛只引用**该项目已有**的门槛或本批刚立下的门槛。
4. 结尾「输出清单」：标识（tag/hash）、每节关键数值。下一轮只读这些。
5. 继承规则一行带过（构建单条、做完打点、更新报告）。
6. 夜间批次：自包含、有优先级、每节有停止与回退；做不完停在最后一个通过的点。
7. 用户的每条观感问题，转成可量化且写入该项目执行规范的检查，而不是一次性口头修补。
8. 不给选择题；给默认做法 + 一个例外出口。

## 真源与边界

真源：用户确认 > 该项目指定的设计/需求原文 > 旧代码（只参考，逻辑按本流程重做）。禁止执行模型在未指定时「看图猜需求」。

结果标签只用该项目已公布的集合（常见为 `PASS` / `FAIL`）。新标签必须先定义再出现。

回归：以上一可追溯点为基线；声明未改的范围必须零意外差异（差异的度量方式跟该项目走）。

平台/硬件未知：标「暂定」，列出「缺它阻塞什么」，不在假设上加活。

中间产物用完即删；只留目标文件、报告与可追溯点。不要主动 commit，除非用户要执行模型提交且该项目批次如此约定。

## 每批要有的产出（由执行模型写）

- 批次报告：做了什么 / 量前量后 / 更正 / 未关闭项
- 未关闭项或模块状态（该项目已有清单则更新，没有则不要新造一套体系）
- 本批新立的规则写进该项目执行规范，不靠聊天记忆
